# ADR 002: I/Oエラーの処理経路の使い分け

## Status

Accepted

## Context

SSS Music PlayerはJavaFXのMVVM構成で、View → ViewModel → AppModel → service → repository の一方向に依存する。
I/Oエラーは主にrepository（SQLite・設定ファイル）とservice（フォルダ走査・ファイル移動・タグ書き込み）で発生する。

エラーの受け口は2つある。1つは画面内の表示（ViewModelの `errorMessageProperty` をラベルにバインド）、もう1つは `App` に置いたFXスレッドの未捕捉例外ハンドラによるダイアログ表示。前者は「どの操作が失敗したか」の文脈を画面上で示せる。後者は文脈を持たないが、バックグラウンドの `Task` や起動時処理など、画面の文脈がない場所からのエラーも一箇所で受けられる。

例外の型にも2系統ある。jOOQは `SQLException` をすべて非チェックの `DataAccessException` に包んで投げる方針で、これは「途中の層は素通りさせ、上位の一箇所で受ける」非局所脱出（Non-Local Exit）を前提にしている。一方、Javaのチェック例外は、通過する各層に `throws` または `catch` を要求することで、直接の呼び出し元に処理を強制する。

これまでの実装では、`LibraryIndexer.scan` はチェック例外 `IOException` を投げつつ、`MusicLibraryAppModel.scanFolder` の `Task` がその失敗を握りつぶし、ユーザーに何も知らされなかった。`DuplicateListViewModel.removeCheckedDuplicates` は `IOException` を `UncheckedIOException` に包んで投げ直し、ダイアログにも画面にも出なかった。また `SqliteLibraryRepository` はjOOQの `DataAccessException` を変換せず素通ししていた。どの層がどの型の例外を投げ、誰が受けるのかが定まっていないことが、これらの取りこぼしの原因である。

## Decision

### 非チェック例外

以下では、I/Oエラーに関する非チェック例外は、ドメインの専用型（`domain.exception`）を用いる。途中に文脈を足す層があることを前提としないため、投げる時点で人間向けのメッセージを持たせる必要がある。

### repository層

**ファイルI/O**は、常に非チェック例外を投げる。チェック例外の場合は、非チェック例外へ変換する。なぜならば、ファイルI/Oに関するエラーは現実的には回復不能だから。例えばjOOQも同様の方針である。なお、jOOQの `SQLException` と `DataAccessException` は `RepositoryException` に翻訳し、jOOQの型を外に出さない。

**ネットワーク処理**は、基本的にはチェック例外を用いて回復をはかる。これはチェック例外の本来の目的とするところである。回復のための再フェッチ処理は、repository層で行う。

### service層

I/Oエラーは、基本的にはrepository層から非チェック例外の形で届く。

service層自身のファイルI/Oエラーは、repository層同様、ドメイン専用の非チェック例外に変換する。

最終的な受け口までの距離で2つの経路に分け、処理の性質で経路を決める。

#### 局所経路

画面の文脈で同期的に実行される処理（例: 重複ファイルの移動）は、非チェック例外をキャッチして、serviceが**チェック例外**へ変換して再スローする。

service層なので、このチェック例外は `domain.exception` に置いたドメインの専用型を用いる。

あるいは、チェック例外の代わりに、ドメイン専用の結果型を返す設計も検討する。結果型は `sealed interface` で成功と各種の失敗を直和型として表し、呼び出し元は `switch` のパターンマッチで全ケースを網羅する。失敗の種類が複数あり、それぞれ画面での見せ方が異なる場合に適する。

チェック例外でも結果型でも、コンパイラによる検査ができる。

ViewModelまたはAppModel側では、チェック例外を捕捉するか結果型を受け取って、人間向けのメッセージを組み立てて `errorMessageProperty` にセットし、Viewが画面内のラベルに表示する。直接の呼び出し元に処理を義務づけるため、チェック例外または結果型を用いる。

#### グローバル経路

バックグラウンドで実行されうる処理（例: ライブラリ走査）と起動時の処理（例: 設定ファイルの読み込み）は、非チェック例外をキャッチせず、そのまま未捕捉例外ハンドラでキャッチされるようにする。

例外を集約する必要がある場合に限り、ドメイン専用の集約先**非チェック例外**へ変換して再スローする。

最終的な受け口は、`App` のFXスレッド未捕捉例外ハンドラ一箇所で、キャッチしたドメイン専用型に従ってダイアログとメッセージを表示する。ドメイン専用型以外の例外も、想定外のエラーとしてスタックトレース付きのダイアログに出す。配布した実行ファイルにはコンソールがなく、標準エラーへの出力はユーザーに届かないためである。

#### 判定に迷う処理

同期実行とバックグラウンド実行の両方がありうる処理は、画面内表示をあきらめてグローバル経路に寄せる。判定は呼び出し元の数ではなく処理の性質で行い、後から呼び出し元が増えても経路を変えない。

## Alternatives

### Alternative 1: すべて非チェック例外に統一し、`App` のダイアログに集約する

serviceもrepositoryも非チェック例外だけを投げ、画面内表示をやめてすべて `App` の未捕捉例外ハンドラで受ける。jOOQの方針と完全に一致し、層ごとの翻訳も `throws` 宣言も不要になる。一方、ユーザー操作の直接の結果であるエラー（重複ファイルの移動失敗など）まで文脈のないダイアログになり、操作した画面の中で原因を示せない。また、局所で処理すべきエラーの `catch` をコンパイラが強制しないため、書き忘れがそのままダイアログや握りつぶしに化ける。操作した画面の中でエラーを示す手段を失うため採用しない。

### Alternative 2: すべてチェック例外に統一する

repositoryからserviceまで一貫してチェック例外を投げる。どの層でも処理の義務づけが効く。しかしjOOQは非チェック例外しか投げないため、repositoryで `DataAccessException` をチェック例外に包み直す変換が必要になる。さらにバックグラウンドの `Task` や起動時処理では、受け口が遠く途中の層に処理できることがないのに、通過する各層へ `throws` を書かせることになる。

そもそも `IOException` がチェック例外なのは、Java初期の「I/Oは回復可能かもしれない」という設計判断によるもので、後年かなり批判されている。Effective Java 第3版の項目71「チェック例外を不必要に使うのを避ける」は、チェック例外を使ってよいのは次の2条件を両方満たすときだけとしている。

1. APIを正しく使っても例外的状況を防げない
2. 例外に直面したプログラマが、回復のために意味のある行動を取れる

どちらかを満たさなければ非チェック例外が適切である。実際のアプリではファイルI/Oの失敗に対して呼び出し側ができることは「諦めて報告する」だけの場合がほとんどで、条件2を満たさない。jOOQやSpringといったライブラリも、KotlinやC#といった言語も、この理由でチェック例外を捨てた。

チェック例外が妥当となるのは、主にネットワーク処理であり、再フェッチを行うことで回復可能性がある。

「回復不能と分かっている場所で非チェックに変える」はこの基準に沿った行為であり、チェック例外への統一はその逆を行く。非局所脱出の利点を捨てるだけになるため採用しない。

### Alternative 3: ViewModel/AppModelの `errorProperty` にすべて集約する

service層が直接AppModel/ViewModelのプロパティに依存する場合、責務が分離されない。

責務を分離するならば、AppModel/ViewModelからservice層のメソッドの呼び出し時に成功・失敗時のラムダを引数で渡すことになる。

ただし、ViewModel/AppModel内のプロパティリスナー経由で発生した例外は `set()` の呼び出し元に伝播せず、スレッドの未捕捉例外ハンドラに送られる。結局 `App` 側のハンドラが必要になり、バックグラウンド処理と起動時処理にもそもそも向いていないため採用しない。

### Alternative 4: 呼び出し元ごとに経路を切り替える

同じservice処理でも、同期呼び出しでは画面内表示、バックグラウンド呼び出しではダイアログ、と呼び出し元ごとに経路を変える。エラーの見せ方を常に最適化できる。しかしserviceに2種類の入口を用意するか、AppModel側でどちらの例外か分岐する必要があり、呼び出し元が増えるたびに経路の判断と実装を足すことになる。ルールが安定しないため採用せず、迷う処理はグローバル経路に寄せる。

## Confidence Level

高い。2つの経路はいずれも既に実装されており（局所: `DuplicateListViewModel` のインライン表示、グローバル: `SettingsException` のダイアログ）、この決定はそれらを一般化して境界を定めるものである。

次の状況では見直す。

- serviceの処理が増え、同期実行とバックグラウンド実行の両方を持つ処理が多くなり、「迷ったらグローバル」の結果として画面内表示が乏しくなった場合。呼び出し元ごとの経路切り替え（Alternative 4）を再検討する
- 失敗の種類が多いserviceが現れ、チェック例外の型が増えて扱いにくくなった場合。`sealed interface` による結果型への移行を優先する
- 未捕捉例外ハンドラ以外の受け口（例: ログ基盤、通知領域）を導入する場合。グローバル経路の受け口の定義を更新する

## Consequences

**良い結果**

- どの層がどの型の例外を投げ、誰が受けるかが決まり、エラーの取りこぼしが設計上起きにくくなる
- 局所経路ではチェック例外または結果型により、処理の義務づけをコンパイラが検査する
- グローバル経路では途中の層が例外を意識しなくてよく、バックグラウンド処理や起動時処理の実装が単純になる

**悪い結果**

- 「迷ったらグローバル」に寄せた処理は、画面内で文脈を示す機会を失う
- グローバル経路の専用例外は、投げる時点で人間向けのメッセージを持つ必要があり、repositoryまたはserviceがメッセージの文言に責任を持つことになる
